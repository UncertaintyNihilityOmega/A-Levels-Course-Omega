# Zero to A* — reorganise into an Organizer + per-course Specialist/Writer setup

## Context
"Zero to A*" is an interactive A Level guide (Markdown chapters → build.js/lib.js → HTML page).
32 of 232 planned chapters and 6 of ~21 widgets exist; WP0 (engine upgrade) was never run.

The user wants a team structure where no chat ever reads the whole project:

| Role | Model | What it does |
|---|---|---|
| Project Organizer (me) | Opus | setup, engine, design, hard problems, assembling the site |
| `<Course>` Specialist | Opus | Course Lead (plans the course, writes the gold chapter) and Reviewer (after every 2 Writer packages, and at the end) |
| `<Course>` Writer | Sonnet | writes chapter packages + widgets by following the Specialist's plan and gold chapter |

### Decisions the user made
- **Where it runs:** Claude Code tab sessions, with the working folder set to `courses/<x>`.
- **Widgets:** each course builds its own.
- **Chapter lists:** Course Specialists may re-plan them; aliases keep old ids working.
- **Output is PC only:** a polished local site that opens by double-click and works offline.
  No claude.ai publishing. The old artifact link is left as it is.
- **Design:** a redesign pass comes first, in an Artifact-quality style. The user approves it, then the format is frozen.
- **Reviews:** the Specialist reviews after every 2 Writer packages.
- **Languages (my choice):**
  - **Node.js** for the engine and course toolkit (the site is HTML/JS, and the engine already exists).
  - **Python** for per-chapter number checks (`fractions`, `math.comb`, `statistics.NormalDist`).
  - Python 3.14 is installed. In shells, `python` hits the Windows Store alias, so every
    command uses **`py`**.

Tell the user plainly:
- All chats share one usage pool. Run 1–3 course chats at a time.
- Cost grows with chapter length, now that there are no word limits.
- When starting course sessions, decline worktree mode so files land in the real folder.

### Course folder (everything a Specialist or Writer sees)
```
CLAUDE.md     auto-loaded. Common rules plus three session types:
                LEAD (Opus), WRITE (Sonnet), REVIEW (Opus).
              Generated by the Organizer from a template.
COURSE.md     scope, syllabus code + URL, board notes, data values (g = 9.81 or 10), depth guidance,
              chapter plan, package list. Written by the Specialist.
course.json   chapter id/title/level/group/order + aliases (Specialist owns)
FACTS.md      subject exam facts + syllabus learning outcomes
STATUS.md     one line per session, e.g. "date · WRITE P3 · 6 chapters · next: REVIEW"
REVIEW.md     the Specialist's findings and fix list for the Writer
REQUESTS.md   asks for the Organizer (engine bug, new block type, styling)
chapters/<id>.md    checks/<id>.py (number re-computation, kept for reviews)    widgets.js
kit/          synced, read-only: STYLE.md (writing spec), WIDGETS.md, EXAMPLE.md (gold chapter),
              LINKS.md (other courses' ids for cross-links), zta.js (one bundled tool), math.otf
preview/      generated course-only page in the final design (gitignored)
```

**Kit commands.** `kit/zta.js` is one esbuild bundle (lib + katex + markdown-it + plot + shell/css/app).
It needs no node_modules:
- `node kit/zta.js check <file>`: maths, blocks, structure checklist, links, plots, widget names
- `node kit/zta.js preview`: builds `preview/index.html`
- `node kit/zta.js widget <name> "<attrs>"`: a test page, viewed in the built-in browser at phone width and in dark mode
- `node kit/zta.js status`: prints the next step:
  - `LEAD` if there is no plan yet
  - `REVIEW` after 2 unreviewed packages
  - `FIX` if REVIEW.md has open items
  - otherwise `WRITE <package>`

### Session flow per course
1. **Specialist LEAD (Opus):**
   - One fetch of the syllabus; write the outcomes into FACTS.md.
   - Write COURSE.md, course.json and the packages (4–8 chapters each, widgets assigned).
   - Review or rewrite any existing drafts.
   - Write one gold-standard chapter and its check.
2. **Writer WRITE (Sonnet):** one package. Per chapter:
   1. Write the whole chapter.
   2. Run `zta check` and `py checks/<id>.py`.
   3. Fix with small edits.

   Then build the package's widgets, run `preview`, add a STATUS line and report in 3 lines.
   The Writer stops and asks for a REVIEW when status says so.
3. **Specialist REVIEW (Opus):**
   - Run every check and sample the chapters.
   - Fix serious errors directly; list the rest in REVIEW.md for the Writer's next session.
   - Adjust COURSE.md guidance if there is drift.
4. **Final REVIEW** once all packages are done; then the Organizer assembles the site.

**Rules for all course chats:**
- Read and edit only this folder.
- No subagents.
- Keep tool output short.
- Never read back a chapter you just wrote.
- Engine needs go into REQUESTS.md.
