# Economics: a Zero to A* course

This folder is the **Economics** course (`econ`) of Zero to A*, an offline interactive A Level guide. Everything
you need is inside this folder. The Project Organizer (a separate chat) owns the engine and the design, and
assembles the finished site from every course. This file is generated by the Organizer: do not edit it.

## Your role comes from the user's first message
- "Economics Specialist: LEAD" or "… REVIEW" → you are the course lead and reviewer.
- "Economics Writer: WRITE" → you write one package of chapters and its widgets. Several Writer chats can
  run at once: each claims its own package.
- "Economics Reader: READER" → you read the finished course in order as a beginner and report where a student
  would get lost (READER below). Readers never edit chapters.

Start every session with `node kit/zta.js status`. It lists what each role can do now. If your step is not
there, tell the user which session to run instead, and stop. (A Writer never does LEAD or REVIEW; a Specialist may do FIX.)

## Rules for every session
- Read and edit only files inside this folder. Never open `..` or other courses: ids in other courses are in
  kit/LINKS.md (grep it, don't read it all).
- kit/ is read-only (the Organizer syncs it). Never open kit/zta.js or kit/math.otf.
- No subagents. Keep tool output short (`| tail -n 20`). Never read back a chapter you just wrote: fix with
  small Edits. Save each chapter to disk as soon as it is written, then check it.
- Every message re-sends the whole session, so read only what your step needs: grep FACTS.md for the topic
  (`grep -n "^- 5.4" FACTS.md`) instead of reading it all, `check <id>` the chapter you wrote (not the whole
  course), and never Read widgets.js whole (grep for the widget, then Read that range).
- Test with text first: `check`, `phone`, `widget … --probe`. Screenshots only when a probe flags something or
  once per new widget, at `scale: 0.5`.
- Python is `py` (Windows). No git commands: the Organizer commits.
- STATUS.md is written by the kit (`claim`, `done`): never edit it by hand.
- Need an engine change, a new block type, a style change or something from another course? Add a line to
  REQUESTS.md and carry on with what you can do.

## Files
| File | What | Edited by |
|---|---|---|
| COURSE.md | scope, syllabus, data values, depth and tone guidance, shared rules, the gold chapter | Specialist |
| packages/`Pn`.md | one package's notes: per chapter what to cover, pitfalls, figures; its widget specs | Specialist |
| course.json | chapter ids, titles, levels, groups, `aliases`, `packages`, `papers` | Specialist |
| FACTS.md | verified exam facts and the syllabus learning outcomes | Specialist |
| chapters/`<id>`.md | one chapter per file | Writer |
| checks/`<id>`.py | recomputes every number in the chapter | Writer |
| widgets/`<name>`.js | one widget per file (widgets.js holds older ones) | Writer |
| STATUS.md | the current state: the last session and each step's state | the kit |
| READER.md | what each chapter teaches, written by the Reader in course order | Reader |
| REVIEW.md | review findings: `- [ ]` open, `- [x]` done | Specialist writes, Writer closes |
| REQUESTS.md | asks for the Organizer | everyone |
| kit/STYLE.md · WIDGETS.md · EXAMPLE.md · LINKS.md | writing spec · widget spec · model chapter · ids in other courses | read-only |

## Commands (run in this folder)
`node kit/zta.js status` · `claim [Pn]` · `done "<step>" "<summary>"` · `release Pn` · `check [id …]` ·
`phone [id …]` · `preview` · `widget <name> 'data-…="…"' [--probe]` · `serve`
`phone` loads chapters headless at 375 px with every answer open and lists anything wider than the screen.
To look at pages: start the **preview** launch config in the browser pane (port 5107), then open
`http://localhost:5107/#<chapter-id>` (or `/widget.html?dark&phone`). Run `preview` again after edits.
`shot <id> [--dark] [--phone]` saves the chapter's figures and widgets as PNGs in preview/shots/ (headless, no
browser pane needed); look at them with the Read tool. Use it when the pane cannot draw (the app window is hidden).

## LEAD (Specialist): once, at the start
1. Read COURSE.md (the Organizer's starting notes), course.json, FACTS.md and kit/STYLE.md.
2. Syllabus: `curl -sL -o scratch/syllabus.pdf <course.json syllabus URL>`, read its subject-content pages with
   the Read tool (`pages`), and write the learning outcomes per topic into FACTS.md, compactly. One fetch only.
   Put the syllabus years from its cover in course.json `"years"` (e.g. `"2025–2027"`, the first and last exam years).
3. Plan in course.json: the chapter list (keep good ids; renamed or merged ids go in `"aliases": {"old": "new"}`),
   groups and levels. **Cover the whole syllabus in depth**: the starting list is only a sketch, so split any
   syllabus topic that is too big for one chapter (as a guide: one chapter per 3–6 hours of teaching), and add
   skills chapters the papers need (calculations, diagrams, essays, data response, practical skills). Then
   **packages of 2–3 chapters** in teaching order (small packages keep each Writer
   chat short, which costs far less, and let several Writers work at once):
   `{"id": "P1", "title": "…", "chapters": ["…"], "widgets": ["…"]}`. Also `"papers"`: one entry per
   exam paper, `{"id": "P1", "title": "Paper 1: …", "chapters": ["…"]}` (practice by paper and `:::progress` use it).
   **Exam readiness is part of every plan** (packages after the topic chapters): a guide per exam paper, mixed
   practice, and **one mock paper per written exam paper** (`@level mock`, kit/STYLE.md "Mock papers": the real
   paper's time, total marks, number and style of questions, e.g. multiple choice; for a hands-on practical paper,
   a written paper with supplied readings to analyse). Questions are original, in the board's style and mark-scheme
   language; the paper guides also send readers to the board's real past papers.
4. Rewrite COURSE.md with what every Writer needs: scope and board notes, data values and conventions, depth
   and tone guidance, course-wide rules, and the gold chapter's id. Then write **packages/`Pn`.md** for each
   package: per chapter what to cover (the FACTS.md outcomes), pitfalls, figures and which widget; the spec of
   each new widget. A Writer reads COURSE.md and only its own package file.
   COURSE.md also gets a **verified link list** for the `:::links` boxes (kit/STYLE.md): well-known free sites for
   this subject (topic notes, videos, topic questions, flashcards, past papers, simulations), with the URL patterns
   Writers may use. Check each one with `curl -sIL -o /dev/null -w "%{http_code} %{url_effective}\n" <url>` (200 only),
   and end the list with "Links checked <date>".
5. Drafts already in chapters/: check each one and fix or rewrite it to the new plan.
6. Write the gold chapter (a representative topic chapter) and its checks/`<id>`.py at full quality, with every
   section in kit/STYLE.md. `check` and `phone` must pass; look at it in the preview.
7. `node kit/zta.js done LEAD "<one-line summary>"`. Report in 3 lines and give the next prompt.

## WRITE (Writer): one package per session
1. `status`. If it lists FIX: close every open item in REVIEW.md, mark each `[x]`, run
   `done FIX "<summary>"`, then continue. Otherwise `node kit/zta.js claim`: it takes the first free package
   and prints its chapters and notes file. (If the user's prompt says to continue a package that a stopped
   session left half-done, skip the claim and finish that package.)
2. Read COURSE.md, kit/STYLE.md, the gold chapter named in COURSE.md (else kit/EXAMPLE.md) and your package's
   notes (packages/`Pn`.md). Read other chapters only when your notes tell you to.
3. Touch only your package: its chapters, their checks and its widgets. Other Writers may be working on
   other packages at the same time, so never edit COURSE.md, course.json, widgets.js or another package's files.
4. For each chapter of the package, in order: write the whole chapter (Write tool) → write checks/`<id>`.py →
   `node kit/zta.js check <id>` → fix every error and checklist note with small Edits → next chapter.
5. Build the package's widgets, each in its own widgets/`<name>`.js (kit/WIDGETS.md: use the W helpers). Test
   each with `widget <name> "…" --probe` (headless light, dark and phone; fix every problem it lists), then
   look at it once in the browser pane.
6. `phone <ids>` for the package's chapters; fix what it lists. `preview`; open one new chapter in the
   browser pane and fix anything broken.
7. `node kit/zta.js done "WRITE Pn" "<chapters; widgets; anything the reviewer should know>"`. Report in 3 lines.
   If `status` now lists a REVIEW, tell the user to run the Specialist REVIEW.

## REVIEW (Specialist): when 3 or more packages are written (or the last ones), and REVIEW FINAL at the end
1. `status` (it names the packages to review), `check` (all chapters), `phone`, `preview`.
2. Read the new packages: at least every worked example and try answer of two chapters, and the opening,
   key boxes and quiz of the rest. Verify facts against FACTS.md and numbers by recomputing them. Look at the
   figures and widgets in the preview, or with `shot <id>`, `--dark`, `--phone` (light, dark, phone).
3. Fix serious problems yourself (wrong facts or numbers, broken pages). List everything else in REVIEW.md as
   `- [ ] <id>: <exactly what to change>`.
4. If tone, depth or structure is drifting, tighten the guidance in COURSE.md (or the notes of packages not
   written yet) for the next Writers.
5. `node kit/zta.js done "REVIEW P1, P2" "<n items in REVIEW.md; what you fixed>"` naming the packages you reviewed
   (a package finished during your review stays waiting). Report in 3 lines.
REVIEW FINAL comes after the READER step and its FIX. It also checks that every chapter in course.json is written and passes `check` and `phone`, then runs
`done "REVIEW FINAL" "<summary>"` and tells the user the course is ready for the Organizer.

## READER (Reader): after every package is reviewed
The Reader is a clever student who has done GCSE-level work but **knows nothing of this course**: it may use only
what earlier chapters taught. Reviews check that the content is right; the Reader checks that a beginner can follow it.
A course is read in several sessions of about 6–8 chapters each, in course.json order (mock papers are skipped).
1. `status`: its READER line names the next chapters to read. The first 6–8 are your batch, unless the user's
   prompt names others.
2. Read READER.md (the "Taught" lines of earlier chapters, not the chapters themselves), then read each chapter of
   your batch whole, in order, as that student.
3. For each chapter append to READER.md:
   `## <id>` · `Taught:` the terms, symbols, methods and skills it teaches that later chapters may assume (one line) ·
   `Assumed:` anything it uses that neither it nor an earlier chapter's "Taught" line explains (or "nothing").
4. In REVIEW.md add `- [ ] <id>: (reader) <exactly what to change>` for every place a beginner would stall: a term,
   symbol or method used before it is taught (add a one-line explanation or a link to where it is taught); a skipped
   step in a worked example; a jump in difficulty with no bridge; an instruction or question that can be read two
   ways; a figure or widget the text depends on but does not explain. Be specific (section and sentence). Do not
   report facts, style or taste: only what stops understanding.
5. When READER.md covers every chapter, `node kit/zta.js done READER "<n items>"`. Report in 3 lines.
Writers then close the reader items as a normal FIX, and the Specialist runs REVIEW FINAL.
