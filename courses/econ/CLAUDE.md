# Economics: a Zero to A* course

This folder is the **Economics** course (`econ`) of Zero to A*, an offline interactive A Level guide. Everything you
need is in this folder. The Project Organizer (a separate chat) owns the engine, the design and the site. This file is
generated by the Organizer: do not edit it.

## Roles (from the user's first message)
- "Economics Specialist: LEAD" or "… REVIEW": course lead and reviewer.
- "Economics Writer: WRITE": one package of chapters and its widgets. Several Writers can run at once, each on its
  own package.
- "Economics Reader: READER": reads the finished course in order as a beginner and reports where a student would
  get lost. Never edits chapters.

Start every session with `node kit/zta.js status`: it lists what each role can do now. If your step is not there,
tell the user which session to run instead, and stop. A Writer never does LEAD or REVIEW; a Specialist may do FIX.

## Rules for every session
- Read and edit only files in this folder. Never open `..` or other courses; ids in other courses are in
  kit/LINKS.md (grep it).
- kit/ is read-only. Never open kit/zta.js or kit/math.otf.
- No subagents. No git (the Organizer commits). Python is `py`.
- Every message re-sends the whole session: read only what your step needs. Grep FACTS.md for the topic, `check`
  only your chapters, never Read widgets.js whole, keep tool output short (`| tail -n 20`), bundle commands.
- Save each chapter as soon as it is written, then check it. Never read back a chapter you just wrote: fix it
  with small Edits. Edit chapters with Write/Edit only (shell scripts eat backslashes).
- Test with text first: `check`, `phone`, `widget … --probe`. Screenshots only when a probe flags something or
  once per new widget, at `scale: 0.5`.
- Scripts that generate a figure or widget go in data/ (scratch/ is not backed up).
- STATUS.md is written by the kit (`claim`, `done`): never edit it.
- Need an engine change, a new block type or something from another course: add a line to REQUESTS.md and go on.

## Commands (in this folder)
`node kit/zta.js status` · `claim [Pn]` · `done "<step>" "<summary>"` · `release Pn` · `check [id …]` ·
`phone [id …]` · `preview` · `widget <name> 'data-…="…"' [--probe]` · `shot <id> [--dark] [--phone]` · `serve`
- `phone`: headless 375 px with every answer open; lists anything wider than the screen.
- Pages: start the **preview** launch config in the browser pane (port 5107), open
  `http://localhost:5107/#<chapter-id>` (or `/widget.html?dark&phone`); run `preview` again after edits.
- `shot`: PNGs of a chapter's figures and widgets in preview/shots/ (open with Read); use it when the pane cannot draw.

## LEAD (Specialist): once, at the start
1. Read COURSE.md (starting notes), course.json, FACTS.md and kit/STYLE.md.
2. Syllabus: `curl -sL -o scratch/syllabus.pdf <course.json syllabus URL>` (one fetch); write the learning outcomes
   per topic into FACTS.md, compactly. Put the first and last exam years in course.json `"years"` (`"2025–2027"`).
3. Real papers: read the front page of one recent question paper per paper and record in FACTS.md exactly what each
   paper prints or allows (data, formulae, calculator, how multiple choice is marked) and its time, marks and
   number of questions. Never assume from the syllabus alone.
4. Plan in course.json:
   - Cover the whole syllabus in depth: one chapter per 3–6 hours of teaching; add skills chapters the papers need.
     Keep good ids; renamed or merged ids go in `"aliases"`.
   - Packages of 2–3 chapters in teaching order: `{"id": "P1", "title": "…", "chapters": ["…"], "widgets": ["…"]}`.
     Each widget belongs to one package.
   - `"papers"`: `{"id": "P1", "title": "Paper 1: …", "chapters": ["…"]}`.
   - Exam readiness after the topics: a guide per paper, mixed practice, and one mock per written paper
     (`@level mock`, kit/STYLE.md "Mock papers": the real time, marks, number and style of questions; a hands-on
     practical paper becomes a written paper with supplied readings). Questions are original, in the board's style
     and mark-scheme language; paper guides point to the board's real past papers.
5. COURSE.md, as rules: scope and board notes, data values and conventions, depth and tone, course rules, board-box
   rule, the gold chapter's id, and a verified link list for `:::links` (well-known free sites; check each with
   `curl -sIL -o /dev/null -w "%{http_code} %{url_effective}\n" <url>`, 200 only; end with "Links checked <date>").
6. packages/`Pn`.md for every package, self-sufficient: outcome numbers and text, what to cover, pitfalls, example
   ideas, figures, widget specs. A Writer reads COURSE.md and only its own package file.
7. Drafts already in chapters/: fix or rewrite them to the plan.
8. Write the gold chapter (a representative topic chapter) and its checks file at full quality with every section in
   kit/STYLE.md; `check` and `phone` pass; look at it in the preview.
9. `node kit/zta.js done LEAD "<one-line summary>"`. Report in 3 lines and give the next prompt.

## WRITE (Writer): one package per session
1. `status`. If it lists FIX: close every open REVIEW.md item, mark each `[x]`, `done FIX "<summary>"`, then go on.
   Otherwise `node kit/zta.js claim` (prints your package). To continue a package a stopped session left half-done,
   skip the claim.
2. Read COURSE.md, kit/STYLE.md, the gold chapter (else kit/EXAMPLE.md) and packages/`Pn`.md. Read other chapters
   only when your notes say so.
3. Touch only your package's chapters, checks, widgets and data scripts. Never edit COURSE.md, course.json,
   widgets.js or another package's files.
4. Per chapter, in order: write it whole → write checks/`<id>`.py → `check <id>` → fix every error and checklist note.
5. Widgets: each in widgets/`<name>`.js (kit/WIDGETS.md, W helpers). Probe each (`widget <name> "…" --probe`: light,
   dark, phone, bad attributes, `a11y:` lines) until clean; look at it once and use it with the keyboard only.
6. `phone <ids>` must pass; `preview` and open one new chapter.
7. `done "WRITE Pn" "<chapters; widgets; notes for the reviewer>"`. Report in 3 lines. If `status` now lists
   a REVIEW, tell the user to run the Specialist REVIEW.

## REVIEW (Specialist): when 3 or more packages are written (or the last ones)
1. `status` (names the packages), `check`, `phone`, `preview`.
2. Look at every figure and widget (preview or `shot`, light, dark, phone; click the interactions,
   then Tab through each widget and use it with the keyboard only). Read every
   worked example and try answer of at least two chapters and the opening, key boxes and quiz of the rest; check
   facts against FACTS.md; recompute numbers. Confirm the Writer's notes at the end of each package file.
3. Fix serious problems yourself (wrong facts or numbers, broken pages, layout). List the rest in REVIEW.md as
   `- [ ] <id>: <exactly what to change>`.
4. If tone, depth or structure drifts, add a rule to COURSE.md (or to unclaimed package notes).
5. `done "REVIEW Pa, Pb, Pc" "<n items; what you fixed>"` naming exactly the packages reviewed. Report in 3 lines.

**REVIEW FINAL** (after READER and its FIX): every chapter in course.json is written and passes `check` and
`phone`; spot-check the FIX rounds; the `Next:` lines form one chain; mock times and totals match FACTS.md; then
`done "REVIEW FINAL" "<summary>"` and tell the user the course is ready for the Organizer.

## READER (Reader): after every package is reviewed
You are a clever student with GCSE-level knowledge who **knows nothing of this course**: use only what earlier
chapters taught. Reviews check correctness; you check that a beginner can follow.
1. `status`: the READER line names the next chapters (course.json order, mocks skipped). Take 6–8 unless the prompt
   names others.
2. Read READER.md (the "Taught" lines), then each chapter of your batch whole, in order.
3. Per chapter append to READER.md: `## <id>` · `Taught:` terms, symbols, methods and skills later chapters may assume
   (one line) · `Assumed:` anything used but not taught here or earlier (or "nothing").
4. In REVIEW.md add `- [ ] <id>: (reader) <exactly what to change>` for every stall: a term, symbol or method used
   before it is taught; a skipped step; a jump with no bridge; an ambiguous question; a figure or widget the text
   relies on but does not explain. Name the section and sentence. Not facts, style or taste.
5. When READER.md covers every chapter: `done READER "<n items>"`. Report in 3 lines.
Writers then close the reader items as a FIX; then REVIEW FINAL.
