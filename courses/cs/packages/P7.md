## cs.databases · Databases: the relational model and normalisation (`@time 6–8 hours`)
Outcomes (FACTS.md 8.1, 8.2): limitations of a file-based approach; features of a relational database that address
them; terms: entity, table, record, field, tuple, attribute, primary key, candidate key, secondary key, foreign
key, relationship (one-to-one, one-to-many, many-to-many), referential integrity, indexing; E-R diagrams; the
normalisation process: 1NF, 2NF, 3NF; explain why tables are or are not in 3NF; produce a normalised design from a
description, a set of data or a set of tables; DBMS features: data management incl. the data dictionary, data
modelling, logical schema, data integrity, data security (backups, access rights for individuals/groups); developer
interface; query processor.
Cover: a flat-file example (a school clubs spreadsheet) showing redundancy, inconsistency, update/insert/delete
anomalies, data dependence, poor security; relational model: tables of entities linked by keys; each term with an
example from one running case; keys (candidate keys, choose a primary key, composite keys, foreign key links, a
secondary key indexed for searching); relationships and resolving many-to-many with a link table; E-R diagrams in the
crow's-foot notation Cambridge papers use (draw as hand SVG); referential integrity (a foreign key value must exist
as a primary key; deleting a parent record); normalisation in full on one realistic unnormalised table (repeating
groups → 1NF; partial dependencies on part of a composite key → 2NF; non-key dependencies (transitive) → 3NF), with
the table design written as `STUDENT(StudentID, Name, FormID)` with the primary key underlined → use bold or "PK:"
since underlining may not render: write the primary key in **bold** and foreign keys marked with an asterisk, and say
so once; DBMS features each tied to the file-based problem it solves; data dictionary contents (table names, field
names, types, sizes, validation rules, keys, relationships); developer interface (forms, reports, query builders);
query processor (takes a query, optimises and executes it).
- `:::def`: entity, table, record (tuple), field (attribute), primary key, candidate key, secondary key, foreign key,
  composite key, relationship, referential integrity, index, normalisation, 1NF, 2NF, 3NF, data dictionary, DBMS,
  logical schema, query processor.
- Pitfalls: 2NF only matters with a composite key; "3NF = no repeated data" is incomplete (no non-key dependencies);
  a foreign key does not have to be unique; many-to-many cannot be implemented directly.
- Exam-style: explain why a given table is not in 3NF (identify the dependency); normalise a set of order data;
  draw the E-R diagram for three tables; give two DBMS features that improve security.
- Figures: hand SVGs of E-R diagrams (two or three entities, crow's foot ends), checked with coordinates.
- Links: W3Schools SQL (for terms), Ada Computer Science, Computerphile. (No SME topic page for 8.)
- `Next: [DBMS and SQL](#cs.sql)`.

## cs.sql · DBMS and SQL (`@time 5–7 hours`)
Outcomes (FACTS.md 8.3): the DBMS uses DDL to create and modify structure and DML for queries and maintenance; SQL is
the industry standard for both; understand a given SQL statement; DDL: CREATE DATABASE, CREATE TABLE with
CHARACTER, VARCHAR(n), BOOLEAN, INTEGER, REAL, DATE, TIME; ALTER TABLE; PRIMARY KEY (field); FOREIGN KEY (field)
REFERENCES Table (Field); DML on at most two tables: SELECT … FROM, WHERE, ORDER BY, GROUP BY, INNER JOIN, SUM,
COUNT, AVG; INSERT INTO, DELETE FROM, UPDATE.
Cover: DDL vs DML; a full CREATE TABLE for two linked tables with keys; ALTER TABLE ADD; each DML statement with
a result table (Markdown) from one running data set (10–15 rows); WHERE with AND/OR, comparison, `LIKE` only if you
say it is beyond the syllabus list (better: avoid); ORDER BY ASC/DESC; aggregate functions with GROUP BY; INNER JOIN
with `ON Table1.Key = Table2.Key` and qualified field names; INSERT INTO with and without field lists; UPDATE … SET
… WHERE; DELETE FROM … WHERE (warn: without WHERE every row goes); dates as `'2026-11-13'`-style literals: use the
format Cambridge mark schemes accept in general terms ("a date in quotes"); reading a given query and stating its
output.
- `:::def`: DDL, DML, SQL, query.
- Pitfalls: `WHERE` before `GROUP BY` before `ORDER BY`; forgetting the join condition; text in quotes, numbers not;
  `COUNT(*)` vs `COUNT(Field)`; UPDATE without WHERE.
- Exam-style: write CREATE TABLE with a foreign key (4); write a query joining two tables with ORDER BY (4); state the
  output of a GROUP BY query; write an UPDATE.
- Widget **cs-sql** after the SELECT section.
- Links: SQLBolt, W3Schools SQL, inner join and group by pages.
- `Next: [Computational thinking and algorithms](#cs.algorithms)`.

## Widget spec: cs-sql
`<div class="widget" data-w="cs-sql" data-db="school"></div>`
- A query builder over one built-in two-table data set (`school`: STUDENT and CLUB/MEMBERSHIP, or `shop`: PRODUCT
  and ORDER, chosen by data-db; data generated by a data/ script and embedded). Controls: SELECT fields (checkboxes,
  or an aggregate SUM/COUNT/AVG of a field), FROM one table or INNER JOIN the second, WHERE (field, operator, value),
  GROUP BY (field or none), ORDER BY (field, ASC/DESC). Shows the SQL it built (in a `<pre>`) and the result table,
  computed in JavaScript. Invalid combinations (a non-grouped field with an aggregate) → a friendly `.w-err` that
  says why.
- Test every control combination's result against `sqlite3` in a data/ script.
