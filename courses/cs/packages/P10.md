## cs.development · The development life cycle and program design (`@time 4–6 hours`)
Outcomes (FACTS.md 12.1, 12.2): purpose of a development life cycle; need for different life cycles depending on the
program; waterfall, iterative and rapid application development (RAD): principles, benefits and drawbacks; the
analysis, design, coding, testing and maintenance stages; structure charts to decompose a problem into sub-tasks
and show the parameters passed between modules (purpose, construct one, derive pseudocode from one); purpose of
state-transition diagrams to document an algorithm.
Cover: why a life cycle (structure, deliverables, quality, planning); each stage (analysis: requirements,
feasibility, the problem; design: algorithms, data structures, interfaces, test plan; coding; testing; maintenance);
waterfall (sequential, sign-off, good for fixed requirements, late working product, costly change), iterative
(repeated cycles of design-build-test, early working versions, feedback), RAD (prototypes, user involvement,
time-boxing, reused components; suits interactive systems with changing requirements; less suited to large
safety-critical systems), choosing one for a scenario; structure charts drawn as Cambridge does (boxes in a hierarchy,
data couples as arrows with an open circle and flags with a filled circle, labelled with parameter names; selection
diamond and iteration arc symbols), parameters by value/by reference shown by direction; deriving procedure/function
headers and calls from a chart (and the reverse); state-transition diagrams (states as circles, transitions as
labelled arrows "event / action", start state arrow, accepting/stop state double circle) for a door lock or a
vending machine, and the matching state-transition table; turning the diagram into a CASE-based pseudocode loop.
- `:::def`: program development life cycle, waterfall model, iterative model, RAD, prototype, structure chart, data
  couple, flag, state-transition diagram, state.
- Pitfalls: arrows in a structure chart show data flow, not order of execution; RAD is not "no planning"; a
  state-transition diagram needs every event from every state the scenario mentions.
- Exam-style: give two benefits and one drawback of RAD for a scenario (3); complete a structure chart from a module
  description (4); write pseudocode headers from a chart (4); complete a state-transition diagram.
- Figures: hand SVGs of a structure chart and a state-transition diagram (coordinates checked; `fig`). The data
  couple arrow symbols: an arrow with a small open circle at the tail (data) and a filled circle (flag).
- Links: SME `12-software-development-/program-development-life-cycle/exam-questions/` and
  `…/program-design-/exam-questions/`, Ada Computer Science.

## cs.testing · Testing, errors and maintenance (`@time 4–6 hours`)
Outcomes (FACTS.md 12.3): ways of exposing and avoiding faults; locate and identify syntax, logic and run-time
errors; correct them; methods of testing: dry run, walkthrough, white-box, black-box, integration, alpha, beta,
acceptance, stub; need for a test strategy and a test plan and their contents; normal, abnormal and
extreme/boundary test data; need for maintenance and the types: perfective, adaptive, corrective; analyse an
existing program and amend it to enhance functionality.
Cover: avoiding faults (good design, modules, meaningful names, comments, defensive validation); the three error
types with pseudocode and Python examples (a Python traceback for a run-time error, run in the checks with the
exception caught); finding a logic error by dry run with a trace table (a full Paper 2 style example with a buggy
algorithm, the trace, the line at fault and the fix); each testing method (what, who, when; white-box tests every
path, black-box tests inputs vs expected outputs; stubs replace unfinished modules; integration tests modules
together; alpha in-house, beta by selected users, acceptance by the client against requirements); test plan table
(test number, purpose, test data, type, expected result, actual result) and choosing data for a range 1–100 (normal 50;
boundary 1 and 100, plus 0 and 101 as the values just outside, labelled as Cambridge does: say "extreme/boundary");
maintenance types with scenarios; amending a program (add a feature to given pseudocode, keep the existing style).
- `:::def`: syntax error, logic error, run-time error, dry run, walkthrough, white-box testing, black-box testing,
  integration testing, stub testing, alpha testing, beta testing, acceptance testing, test plan, test strategy, normal
  data, abnormal data, extreme data, boundary data, perfective maintenance, adaptive maintenance, corrective
  maintenance.
- Pitfalls: a run-time error is not a syntax error even if the program "crashes"; abnormal data should be rejected;
  adaptive (change in environment/requirements) vs perfective (improve performance/usability).
- Exam-style: identify and correct three errors in given pseudocode (one of each type where possible) (6); complete a
  test plan for a validation function; describe stub testing; state the type of maintenance for scenarios.
- Links: SME `12-software-development-/program-testing-and-maintenance/exam-questions/`, Python Tutor.
